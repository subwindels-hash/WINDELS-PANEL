# Module 13 — deployment, actually deployed

*Branch `arena/01a04558-windels-panel`. Follows module 12 (performance).*

`verify_deployment_package.sh` has long proved the archive is *shaped* right:
the framework ships as real files, there is no composer step, `.env` alone
configures everything, the encryption keys survive a move between hosts. What
nobody had ever done is the thing an operator actually does:

1. extract `application-deployment.zip` into an empty account,
2. import `database/marvysocials.sql` into a brand new, empty database,
3. write `.env`,
4. open the site and sign in with the credentials printed in the file's header.

This module does that, end to end, against the extracted tree — never the
working copy — with its own database and its own web server. It found three
things.

---

## 1. Nothing had ever executed the shipped SQL

`marvysocials.sql` is generated by one script and checked as *text* by another.
A dump that parses is not a dump that applies.

`tools/devdb/import_sql.cjs` now feeds it to the dev database over the MySQL
client protocol — the same wire the application uses — splitting statements
with a parser that understands quotes, backticks and comments (a seed file full
of JSON defaults is exactly where naive `;` splitting breaks).

The result is the good news: **502 statements, 502 applied, 0 failed**, and the
imported database carries the schema, the migration bookkeeping (so nothing
replays), 4 roles, 57 permissions, the payment methods and the three documented
accounts. The site then boots on it, the homepage and catalogue render, and
**both documented passwords work** — administrator and customer — with every
admin screen rendering on a database that has never had a migration run against
it.

## 2. The dev server served `.env`

The deployment check asked "is `.env` reachable over HTTP?" and got **200**.

The shipped `.htaccess` is correct — it denies dotfiles twice over (rewrite rule
and `FilesMatch`, so it holds even without `mod_rewrite`) and denies `*.sql`.
The 200 came from the *dev server*, which reads files straight from disk and
knows nothing about `.htaccess`. On a laptop that is careless. In this sandbox,
where the port is published as a preview URL, it meant every credential in
`.env`, the production dump with the seeded administrator hash, and everything
under `storage/` were downloadable by anyone with the link.

`tools/devserver/server.mjs` now refuses the same list the shipped Apache and
nginx configs refuse — dotfiles, `*.sql|sqlite|zip|gz|log`, and
`application/ system/ vendor/ storage/ tools/ tests/` — stated once in an
`isDenied()` function next to a comment explaining which production config each
rule mirrors. The check asserts **both** halves: the `.htaccess` contains the
rules a real host obeys, *and* the served response refuses.

## 3. Every VTU purchase in a customer's history was a dead link

`ActivityFeed` maps each domain to its detail-page URL. `VTU` pointed at
`dashboard/vtu/<public_id>` — which has no route. The receipt lives at
`dashboard/vtu/receipt/<public_id>`.

So on the unified history page, the panel's second-largest domain linked every
row to a 404. It had never been caught because the demo dataset carried no VTU
rows for the feed to render; it appeared the moment an end-to-end check made a
real airtime purchase and left one behind.

Fixed, and pinned: `ActivityFeedRoutesTest` resolves every prefix in both maps
(customer and staff) against `config/routes.php` the way CodeIgniter matches
them, so the next domain added cannot ship with the same fault.

## 4. How it was verified

### `tools/devserver/deployment_check.mjs` — 35 checks

Extracts the package, starts a private database, imports the shipped SQL over
the wire, writes `.env`, boots a web server rooted at the extracted account,
and then: homepage, catalogue, `deploy-verify.php`, admin sign-in with the
documented password, four admin screens, customer sign-in, customer dashboard,
and the install surface (setup wizard closed, `.env` refused, dump not
downloadable, storage not browsable).

`deploy-verify.php`'s own summary is used as an assertion: **38 passed, 2
warnings, 1 failed**, and the check requires every failure to be one of the two
schema-*shape* checks — column types and index/foreign-key objects — which
SQLite behind a protocol translator cannot satisfy and any MySQL host will. The
warnings are `intl` missing and a non-https base URL, both environmental.

```
node tools/devserver/deployment_check.mjs
35/35 checks passed
```

### Tests

`tests/unit/ActivityFeedRoutesTest.php` (4 tests) — every history link
resolves, for customers and staff, and the VTU link points at the receipt.

**Suite: 1392 tests, 16558 assertions, 0 failures, 1 skipped.**
`link_crawl` now visits 160 pages with **0 problems** (it was reporting the two
dead VTU links), `image_audit` 17 images 0 broken, `smoke` 24/24, `journey`
38/38, `page_audit` 0 failing pages.

## 5. Still open

- **Apache itself is not exercised.** The `.htaccess` rules are asserted as
  text; whether a given host has `mod_rewrite` or `mod_authz_core` is a
  property of that host. `docs/cpanel-deployment.md` lists the manual checks,
  and both deny-mechanisms ship so that either alone is sufficient.
- **`VP_DB_STRICT=inherit`** is the one line in the simulated `.env` a real
  account would not need: the panel sends `SET sql_mode=STRICT_ALL_TABLES` as a
  connection init command, which real MySQL answers and the dev database cannot
  (the wasm client aborts on the reply). Production keeps strict mode.
- **The two schema-shape failures** in `deploy-verify.php` can only be cleared
  on real MySQL. They are precisely the checks that would catch a partially
  imported dump on a real host, so they stay.
